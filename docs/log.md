# 開発ログ: トークン最適化の記録

各段階で「何を変えたか・なぜ減ったか/減らなかったか」を記録する。数値は bench/results.csv / bench/report.md。

## 測定条件
- 対象: lectures/LD9.pdf(論理回路設計 第9回 Memory Logic, 48ページ, スライド資料・日英併記, 画像134枚)
- モデル: Sonnet(v3 の要点抽出のみ Haiku)/ 各バージョン3回(合計トークンのばらつきが20%超なら5回)
- `claude -p --output-format json --strict-mcp-config` で毎回新規セッション。CLAUDE.md はバージョン間で変更しない
- 合計トークン = modelUsage の全モデル合算(入力+出力+キャッシュ作成+キャッシュ読込)

## 前処理 extract.py の効果(LD9)
| | 文字数 |
|---|---|
| PDF から抽出したまま(--raw) | 16,351 |
| ノイズ除去後 | 14,127(−14%) |

除去したもの: 毎ページの日付・ページ番号、二重に抽出されるスライドタイトル、繰り返し出る Outline スライド(5ページ分を「p.N と同内容」に置換)。
章分割: 繰り返し出る Outline スライドを区切りとみなし 7 チャンクに分割。

## 固定オーバーヘッド(baseline)
「ok と返すだけ」の1往復: **33,890 tokens / $0.038**。システムプロンプト・ツール定義・CLAUDE.md・スキル一覧など、
どのバージョンでも必ずかかる分。これより下には減らせない。

## v0(基準): PDF をそのまま Read で読ませる
**変えたこと**: なし(基準)。Read ツールに PDF を 20 ページずつ渡す(PDF はページ画像+テキストとしてモデルに入る)。
前提として poppler(pdftoppm)が必要だった。

**結果(LD9, 5回)**
| 指標 | 平均 (最小–最大) |
|---|---|
| 合計トークン | 434,620 (413,304–517,147) |
| 内 キャッシュ作成 | 約 77,500 |
| 内 キャッシュ読込 | 350,619 (330,326–431,706) |
| 出力 | 約 6,400 |
| コスト換算 | $0.409 ($0.400–$0.428) |
| 時間 | 59 秒 |
| 網羅率 / 根拠付き率 | 99% / 100%(r4 のみ「タイミング違反」が欠落) |

**分析**
- 合計の **約8割がキャッシュ読込**。エージェントは1ターンごとにそれまでの文脈(システムプロンプト+読み込んだPDF)を
  丸ごと読み直すので、「文脈の大きさ × ターン数」で膨らむ。PDF を読み込んだ後の文脈は約7.7万トークン。
- 3回目だけ 8 ターン(他は 7 ターン)で、キャッシュ読込が約10万増えた → 合計のばらつき 25% の原因。
  一方コストは +5% しか増えていない(キャッシュ読込は通常入力の約1/10の単価)。
  → **トークン数とコストの両方で比較する必要がある**ことを示す例。
- ばらつきが 20% を超えたので、ルールどおり5回に増やした。
- 改善の方向: (1) 文脈に入れるPDFの量そのものを減らす(画像→テキスト、ノイズ除去) (2) ターン数を減らす。

## v1: PDF を事前にテキスト化してから読ませる
**変えたこと**: Read で PDF を直接読む代わりに、`extract.py --raw` でページ単位のテキスト(`--- p.N ---` 区切り)に変換し、
そのテキストファイルを1回で読む。ノイズ除去はまだしない。
(準備として、`claude -p` で extract.py を実行できるよう、フォルダの信頼設定と `.claude/settings.json` の許可ルールを有効にした)

**結果(LD9, 3回)**
| 指標 | v0 | v1 | v0比 |
|---|---|---|---|
| 合計トークン | 434,620 | **208,966** | **−52%** |
| 内 キャッシュ作成 | 約 77,500 | 約 30,100 | −61% |
| 内 キャッシュ読込 | 350,619 | 174,164 | −50% |
| ターン数 | 7〜8 | 6 | |
| コスト換算 | $0.409 | **$0.185** | **−55%** |
| 時間 | 59 秒 | 42 秒 | −29% |
| 網羅率 / 根拠付き率 | 99% / 100% | 98% / 100% | 同等(r3 のみ「リセット信号」欠落) |

**なぜ減ったか**
- PDF を Read で読むと、各ページが **画像としても** 文脈に入る(LD9 は画像134枚のスライド)。テキストだけにしたことで、
  1回の文脈に入る量(≒キャッシュ作成)が約7.7万 → 約3万トークンに減った。
- 文脈が小さくなったので、毎ターンの読み直し(キャッシュ読込)も半分になった。PDF を20ページずつ3回読んでいたのが、
  テキストファイル1回の読み込みになり、ターン数も 7〜8 → 6 に減った(extract.py の実行で1ターン増えた分を差し引いても減った)。
- ばらつきは 0.5% と非常に小さい(ターン数が毎回同じだったため)。
- 品質は落ちていない。スライドの図の中身は読めなくなるが、LD9 は日本語の解説文が各ページにあるため影響が小さかったと考えられる。

**減らなかった/注意点**
- 小さいサンプルPDF(文字だけ10ページ)では、v1 のほうが v0 より多かった(186,631 vs 165,159)。画像が少ない資料では
  テキスト化で減る分より、extract.py の実行で増える1ターン分のほうが大きいため。**効果は資料の性質に依存する。**

## v2: ノイズ除去 + 章単位で要点抽出 → 統合
**変えたこと**: `extract.py --split` でノイズ除去(文字数 −14%)と7チャンクへの章分割を行い、
チャンクごとに「読む → 要点を `work/LD9/points/chunk_NN.md` に書く」を繰り返してから、要点だけを材料にノートを統合する。

**結果(LD9, 5回。最初の3回のばらつきが 39.6% だったため追加)**
| 指標 | v1 | v2 | v1比 | v0比 |
|---|---|---|---|---|
| 合計トークン | 208,966 | 342,243 (267,597–377,066) | **+64%** | −21% |
| 内 キャッシュ作成 | 約 30,100 | 約 34,400 | +14% | |
| 内 キャッシュ読込 | 174,164 | 296,506 | +70% | |
| 出力 | 約 4,700 | 約 11,400 | +143% | |
| ターン数 | 6 | **19〜21** | 約3倍 | |
| コスト換算 | $0.185 | $0.281 | **+52%** | −31% |
| 時間 | 42 秒 | 79 秒 | +88% | |
| 網羅率 / 根拠付き率 | 98% / 100% | 100% / 100% | 微増 | |

**なぜ減らなかったか(v1 より増えた)**
- ノイズ除去で入力テキストは14%減ったが、**ターン数が 6 → 約20 に増えた** 影響のほうがはるかに大きい。
  チャンクごとに Read と Write の2ターンずつ使い、それが7チャンク分続く。
- 同じ会話の中で順番に読むので、**読んだチャンクは最後まで文脈に残り続ける**。後半のターンほど文脈が大きく、
  そのたびにキャッシュ読込が積み上がる。分割しても「一度に読む量」が減るだけで「文脈に残る量」は減らない。
- 要点ファイルを書き出す分、出力トークンも2倍以上になった。
- ばらつき(トークン数 ±40%、コスト ±17%)の原因もターン数(19〜21)。終盤の1ターンは文脈が大きいので、
  2ターンの差でキャッシュ読込が約10万変わる。

**良かった点**
- 網羅率は 100%(5回とも)。章ごとに丁寧に拾うので、v0/v1 で時々漏れた用語(タイミング違反・リセット信号)も落ちなかった。

**次への示唆**
- 「分割」は、分割した部分を **別の文脈で処理して、結果だけを持ち帰る** ときに初めて効く。→ v3 でサブエージェントに任せる。

## v3: 章ごとにサブエージェント(Haiku)へ委譲 → メイン(Sonnet)で統合・問題作成
**変えたこと**: v2 と同じ7チャンクを、`chunk-summarizer`(model: haiku, tools: Read のみ)サブエージェント7つに
同時に渡す。各サブエージェントは自分のチャンクだけを読み、30行以内の要約を返す。メインはチャンク原文を一切読まず、
要約だけでノートの統合と確認問題の作成を行う。15ページ以下の資料ではサブエージェントを使わない。

**結果(LD9, 5回。最初の3回のばらつきが 93.6% だったため追加)**
| 指標 | v1 | v2 | v3 | v0比 |
|---|---|---|---|---|
| 合計トークン | 208,966 | 342,243 | 337,038 (271,848–526,241) | −22% |
| 内 Sonnet / Haiku | 208,966 / 0 | 342,243 / 0 | 265,580 / 71,458 | |
| コスト換算 | $0.185 | $0.281 | **$0.191** ($0.179–$0.215) | **−53%** |
| 時間 | 42 秒 | 79 秒 | 50 秒 (22–64) | |
| 網羅率 / 根拠付き率 | 98% / 100% | 100% / 100% | 99% / 100% | |

各回の内訳(会話記録から集計):
| 回 | メインの API 呼び出し | Sonnet | Haiku | 時間 |
|---|---|---|---|---|
| r1 | 5 | 200,062 | 71,786 | 50 秒 |
| r2 | 6 | 237,206 | 70,416 | 57 秒 |
| r3 | **11** | **455,403** | 70,838 | 22 秒 |
| r4 | 5 | 201,012 | 73,165 | 64 秒 |
| r5 | 6 | 234,217 | 71,084 | 57 秒 |

**何が効いたか**
- **Haiku 側は安定して約7.1万トークン、コストは約 $0.009**(全体の5%未満)。7チャンク分の原文読み込みを
  安いモデルの別文脈に追い出せた。各サブエージェントの固定分は約5千トークンと、メイン(約3.3万)よりずっと小さい。
- メインの文脈には要約しか入らないので、1回の呼び出しは約4万トークン(うち約3.3万は固定オーバーヘッド)に収まった。

**なぜ v1 より安くならなかったか**
- メインのコストは「呼び出し回数 × 固定オーバーヘッド(約3.3万)」でほぼ決まる。v1 は6回、v3 も5〜6回で、ほぼ同じ。
  LD9(約1.4万字)程度の長さでは、原文を読む分(v1 で約1万トークン)より固定オーバーヘッドのほうが大きく、
  本文を追い出す効果が出にくい。
- **ばらつきの原因**: r3 だけ、サブエージェントがバックグラウンド実行になり、1つ終わるたびにメインが起こされて
  「待機ターン」が発生した(メインの呼び出しが11回)。トークンは約2倍になったが、増えたのは安いキャッシュ読込なので
  コストは +20% 程度。逆に、待たずに並列で進んだため時間は最短(22秒)だった。

**結論**
- コストで見ると v1 と v3 はほぼ同じ(v0 比 −55% / −53%)。トークン数で見ると v1 が最も少ない。
- v3 の利点は「メインの文脈が資料の長さに比例して増えない」こと。資料が長くなるほど v1 との差が開くはずで、
  LD9 程度の長さではまだその差が出ない。品質(網羅率 99%)は v1 と同等以上を保てた。
